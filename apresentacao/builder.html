Sobre o Padrão
O que é o Padrão Builder?

Classificação GoF: Padrão Criacional (Creational Pattern)
Definido originalmente por Gamma, Helm, Johnson e Vlissides no livro de 1994.

O Builder separa o algoritmo de construção de um objeto complexo da sua representação final. Isso permite que o mesmo processo de montagem produza diferentes variantes de um objeto.

Diferente de uma factory que entrega o objeto em uma única chamada, o Builder monta o objeto passo a passo — cada etapa configura uma parte específica — e só materializa o produto ao chamar construir().

Factory Method
Delega a criação a subclasses
Builder
Monta passo a passo
← nosso foco
Abstract Factory
Famílias de objetos
Os 4 participantes GoF
Builder
Interface que declara os métodos de configuração para cada parte do produto. Define o contrato de construção.
ConcreteBuilder
Implementa a interface Builder, acumula o estado interno e executa validações em construir().
Director
Orquestra a sequência de chamadas ao Builder. Conhece o processo, não o produto resultante.
Product
O objeto complexo sendo construído. Seu construtor é restrito — só pode ser criado via Builder.
Quando Aplicar
Casos de uso do Padrão Builder
01
Objetos com muitos parâmetros
Quando um objeto exige 5 ou mais parâmetros no construtor, o Builder substitui a lista confusa por uma API fluente e nomeada.
02
Parâmetros opcionais
Evita a passagem explícita de null para campos opcionais. Apenas os métodos necessários são chamados.
03
Validação centralizada
O método construir() é o único ponto de validação — garante que nenhum objeto inválido seja criado antes da persistência.
04
Múltiplas representações
O mesmo Director pode usar diferentes ConcreteBuilders para produzir variantes do mesmo tipo de produto sem alterar o processo.
Exemplos no ecossistema Java

StringBuilder  ·  HttpClient.newBuilder()  ·  Stream.builder()  ·  Locale.Builder

Exemplos no Spring

UriComponentsBuilder  ·  MockMvcRequestBuilders  ·  SecurityFilterChain via lambda

O Problema
Código sem Builder — o anti-padrão no AgroPlace

Como ficaria a entidade Anuncio e sua criação sem o padrão Builder:

Anuncio.java — construtor telescópico
public class Anuncio {

  public Anuncio( // ← construtor público, 12 parâmetros
      ContaUsuario conta,
      String titulo,
      String especie,
      String raca,       // ← opcional, mas obrigatório aqui
      int quantidade,
      BigDecimal pesoMedioKg,
      Integer idadeMediaMeses,
      SexoAnimal sexo,
      BigDecimal precoUnitario,
      String cidade,
      String estado,

    // ... 11 atribuições sem nenhuma validação

Campos opcionais forçam null explícito na chamada
Nenhuma validação — objeto inválido chega ao banco
Construtor público expõe a criação a qualquer código
A Solução
Código com Builder — como o AgroPlace resolve

ConcreteBuilder — acumula campos e valida tudo antes de criar o objeto:

AnuncioConcretoBuilder.java — construir() + validar()
@Override
public Anuncio construir() {
  validar(); // ← único ponto de validação
  return new Anuncio(this); // construtor package-private
}

private void validar() {
  if (conta == null)
    throw new IllegalStateException("Conta obrigatória");
  if (titulo == null || titulo.isBlank())
    throw new IllegalStateException("Título obrigatório");
  if (quantidade < 1)
    throw new IllegalStateException("Mínimo 1 animal");
  if (precoUnitario.compareTo(BigDecimal.ZERO) <= 0)
    throw new IllegalStateException("Preço deve ser positivo");
  if (estado.length() != 2)
    throw new IllegalStateException("Estado inválido (use UF)");
}

Director + Serviço — código limpo, sem conhecer os campos:

ServicoAnuncioPadrao.java — com Builder
@Override
public RespostaAnuncio criar(
    ContaUsuario conta,
    RequisicaoAnuncio req) {

  DiretorAnuncio diretor =
    new DiretorAnuncio(
      new AnuncioConcretoBuilder() // ← injeção da impl
    );

  Anuncio anuncio =
    diretor.construirDaRequisicao(conta, req);
    // ↑ se inválido, lança exceção aqui — antes do save

  return montarResposta(
    repositorio.save(anuncio) // ← sempre válido
  );
}

DiretorAnuncio.java
public class DiretorAnuncio {

  private final AnuncioBuilder builder;
  // ↑ depende da interface, não da implementação

  public DiretorAnuncio(AnuncioBuilder b) {
    this.builder = b;
  }

  public Anuncio construirDaRequisicao(
      ContaUsuario conta,
      RequisicaoAnuncio req) {
    return builder
      .conta(conta).titulo(req.titulo())
      .especie(req.especie()).raca(req.raca())
      .quantidade(req.quantidade())
      .pesoMedioKg(req.pesoMedioKg())
      .sexo(req.sexo())
      .precoUnitario(req.precoUnitario())
      .cidade(req.cidade()).estado(req.estado())
      .descricao(req.descricao())
      .construir(); // ← valida e cria
  }
}

Cada tipo de usuário tem campos específicos do seu domínio. O Builder garante que cada perfil seja montado com as regras corretas sem compartilhar lógica desnecessária.

PerfilProdutorConcretoBuilder.java — construir() + validar()
@Override
public PerfilProdutor construir() {
  validar();
  return new PerfilProdutor(this);
}

private void validar() {
  if (conta == null)
    throw new IllegalStateException(
      "Conta é obrigatória");
  if (nomePropriedade == null
      || nomePropriedade.isBlank())
    throw new IllegalStateException(
      "Nome da propriedade é obrigatório");
  if (cidade == null || cidade.isBlank())
    throw new IllegalStateException(
      "Cidade é obrigatória");
  if (estado == null
      || estado.length() != 2)
    throw new IllegalStateException(
      "Estado inválido");
}

// getters utilizados pelo construtor de PerfilProdutor
public ContaUsuario getConta() { return conta; }
public String getNomePropriedade() { return nomePropriedade; }

Vantagens
Por que Builder é ideal para o AgroPlace
✦
Legibilidade do código
Cada campo é nomeado explicitamente na chain fluente. Não há dúvida se o 4º argumento é peso ou quantidade.
✦
Validação fail-fast
construir() é a única porta de saída. Nenhum objeto inválido chega ao repositório — regras protegidas na camada de domínio.
✦
Campos opcionais sem null
Campos como raça e descrição simplesmente não são chamados. Sem sobrecarga de construtores e sem null explícito.
✦
Encapsulamento total do produto
O construtor de Anuncio é package-private. Impossível criar um produto malformado fora do Builder.
✦
Extensibilidade
Adicionar um campo ao Anuncio requer apenas um novo método na interface e no ConcreteBuilder. O Director e o Serviço não mudam — Open/Closed Principle.
✦
Testabilidade
Cada ConcreteBuilder pode ser testado isoladamente. É possível criar um MockBuilder implementando a interface para testes de Director sem dependências reais.
✦
Separação de responsabilidades
O Serviço cuida das regras de negócio. O Director cuida do processo de montagem. O ConcreteBuilder cuida dos campos e validações.
✦
Consistência entre módulos
Os 3 módulos seguem o mesmo padrão. Qualquer desenvolvedor que entra no projeto entende imediatamente a estrutura.
Princípios SOLID
Builder e SOLID — como se complementam
Princípio Como o Builder aplica no AgroPlace Evidência no código
S — SRP Builder cuida exclusivamente da montagem e validação. Serviço cuida da regra de negócio. Director cuida do processo. Cada classe tem uma única razão para mudar. ServicoAnuncioPadrao não conhece campos de Anuncio
O — OCP Para adicionar fotoPrincipal ao Anúncio, basta um novo método na interface e no ConcreteBuilder — sem alterar Director ou Serviço. Interface AnuncioBuilder define contrato extensível
L — LSP Qualquer novo ConcreteBuilder que implemente AnuncioBuilder pode substituir AnuncioConcretoBuilder no Director sem quebrar o comportamento. DiretorAnuncio depende apenas da interface
I — ISP Cada Builder tem apenas os métodos do seu produto. ContaUsuarioBuilder não tem métodos de AnuncioBuilder — interfaces enxutas e coesas. 5 interfaces distintas para 5 entidades
D — DIP DiretorAnuncio recebe um AnuncioBuilder (interface) no construtor, não um ConcreteBuilder. Depende da abstração, não da implementação. new DiretorAnuncio(new AnuncioConcretoBuilder())

Conclusão
Builder no AgroPlace — resumo
Problema resolvido
Os 3 módulos criavam objetos com 7 a 12 parâmetros posicionais. O Builder substituiu por uma API fluente nomeada, segura e extensível.
Validação garantida
validar() no ConcreteBuilder garante que nenhum objeto inválido chega ao repositorio.save() — fail-fast antes da persistência.
Arquitetura limpa
Padrão aplicado em sincronia com Clean Architecture — Builder vive no domínio, Director na aplicação, sem vazamento de dependências.
