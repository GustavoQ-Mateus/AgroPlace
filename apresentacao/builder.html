Padrão Builder

"Separar a construção de um objeto complexo da sua representação, de modo que o mesmo processo de construção possa criar diferentes representações."

— Gang of Four, Design Patterns, 1994

Classificação
Padrão de Criação (Creational)
Aplicado em
AgroPlace — 3 módulos do backend
Linguagem
Java 17 / Spring Boot 3.4.5
Contexto
Os 5 padrões de criação GoF

Todos resolvem o problema de como criar objetos — cada um para um cenário diferente

Singleton
Garante uma única instância global da classe — acesso controlado em toda a aplicação
Factory Method
Delega a decisão de qual objeto criar para subclasses especializadas
Abstract Factory
Cria famílias de objetos relacionados sem especificar classes concretas
Builder ← escolhido
Constrói objetos complexos passo a passo, separando montagem da representação
Prototype
Cria novos objetos clonando instâncias existentes

Por que Builder para o AgroPlace?
A entidade Anuncio exige 12 parâmetros. A entidade ContaUsuario exige 7. Com construtores convencionais, o código se torna ilegível e impossível de validar com segurança antes de salvar no banco.

Antes de entrar no código
Uma analogia do dia a dia

Pense no formulário de publicação de um anúncio no AgroPlace

Sem Builder — Construtor direto
É como ligar para o produtor e falar tudo de uma vez, na ordem certa, sem esquecer nenhum parâmetro:

"Olá, quero um lote — Conta JC, título Nelore Macho, espécie BOVINO, raça Nelore, 50 cabeças, 420 kg, 24 meses, MACHO, R$3800, Sobral, CE, vacinados..."
new Anuncio(conta, "Nelore Macho", "BOVINO",
  "Nelore", 50, new BigDecimal("420"),
  24, SexoAnimal.MACHO, new BigDecimal("3800"),
  "Sobral", "CE", "Vacinados");
Com Builder — Formulário passo a passo
É como preencher um formulário online: você informa cada campo pelo nome, na ordem que quiser, e campos opcionais ficam em branco. Só quando clica em "Publicar" o sistema valida e salva.

Se um campo obrigatório estiver vazio, você recebe um erro específico antes de salvar.
builder.conta(conta).titulo("Nelore Macho")
  .especie("BOVINO").quantidade(50)
  .precoUnitario(new BigDecimal("3800"))
  .cidade("Sobral").estado("CE").construir();

A chave: no Builder, o objeto só existe quando está completo e válido — assim como um anúncio só vai ao catálogo após passar pela validação.

O Problema
O anti-padrão: telescoping constructor

Construtor com 12 parâmetros posicionais — sem nomes, sem validação, sem legibilidade:

// ANTI-PADRÃO — quem lê sabe o que é o parâmetro 5?
new Anuncio(
  conta,
  "Lote Nelore Macho",   // título
  "BOVINO",               // espécie
  "Nelore",               // raça
  50,                     // quantidade
  new BigDecimal("420.00"),// peso
  24,                     // idade
  SexoAnimal.MACHO,
  new BigDecimal("3800.00"),// preço
  "Sobral", "CE", "Vacinados"
);

Consequências diretas:

Ilegibilidade
Impossível saber qual argumento é qual campo sem IDE. Parâmetro 5 é quantidade ou peso?
Sem validação
Nenhum ponto central para checar pré-condições. Objeto inválido chega ao banco de dados.
Acoplamento
Toda chamada depende da ordem exata. Trocar dois campos compila normalmente — bug silencioso.
Campos opcionais
Forçado a passar null para raca e descricao quando não informados.
A Solução — GoF
Os 4 participantes do padrão Builder

Cada participante tem uma responsabilidade única e bem definida

1 · Interface
Builder
Declara os métodos de configuração para cada parte do produto. Define o contrato de montagem — o que pode ser configurado, sem saber como.
AnuncioBuilder · ContaUsuarioBuilder
2 · Implementação
ConcreteBuilder
Implementa a interface Builder. Acumula o estado internamente e executa validar() dentro do método construir() — objeto inválido nunca é criado.
AnuncioConcretoBuilder · ContaUsuarioConcretoBuilder
3 · Orquestrador
Director
Conhece a sequência de montagem. Chama os métodos do Builder na ordem correta. O cliente (serviço) delega para o Diretor — não conhece os campos do objeto.
DiretorAnuncio · DiretorContaUsuario
4 · Resultado
Product
O objeto complexo sendo construído. Seu construtor é package-private — só pode ser instanciado via Builder. Nenhum código externo cria um produto inválido.
Anuncio · ContaUsuario · PerfilProdutor
Como funciona na prática
Fluxo de execução — passo a passo

Do clique em "Publicar Anúncio" até o objeto salvo no banco

1
Cliente
ServicoAnuncio chama o Diretor passando a requisição HTTP e a conta logada
2
Director
DiretorAnuncio chama cada método do Builder na ordem correta
3
ConcreteBuilder
Acumula os campos internamente. Ao chamar construir(), executa validar() — lança exceção se inválido
4
Product
Anuncio válido e completo é retornado. Serviço passa para o repositório.save()
// ServicoAnuncioPadrao.java — o serviço não conhece os campos do Anuncio
DiretorAnuncio diretor = new DiretorAnuncio(new AnuncioConcretoBuilder());

Anuncio anuncio = diretor.construirDaRequisicao(conta, req); // 1 linha — limpo e seguro

return repositorio.save(anuncio); // só chega aqui se o anuncio for válido

O serviço não sabe nada sobre os 12 campos do Anúncio. Só delega ao Diretor — se os campos mudarem, o serviço não precisa ser alterado.

Implementação — Módulo Anúncio
AnuncioBuilder + DiretorAnuncio
AnuncioBuilder.java — a interface
public interface AnuncioBuilder {
  AnuncioBuilder conta(ContaUsuario conta);
  AnuncioBuilder titulo(String titulo);
  AnuncioBuilder especie(String especie);
  AnuncioBuilder raca(String raca);       // opcional
  AnuncioBuilder quantidade(int n);
  AnuncioBuilder pesoMedioKg(BigDecimal v);
  AnuncioBuilder sexo(SexoAnimal sexo);
  AnuncioBuilder precoUnitario(BigDecimal v);
  AnuncioBuilder cidade(String cidade);
  AnuncioBuilder estado(String estado);
  AnuncioBuilder descricao(String desc);  // opcional
  Anuncio        construir();              // valida e cria
}

Cada método retorna AnuncioBuilder — permite encadear chamadas fluentes (fluent API)

DiretorAnuncio.java — o orquestrador
public class DiretorAnuncio {

  private final AnuncioBuilder builder;

  // Recebe a interface — não a implementação
  public DiretorAnuncio(AnuncioBuilder b) {
    this.builder = b;
  }

  public Anuncio construirDaRequisicao(
      ContaUsuario conta,
      RequisicaoAnuncio req) {

    return builder
      .conta(conta)
      .titulo(req.titulo())
      .especie(req.especie())
      .raca(req.raca())        // pode ser null
      .quantidade(req.quantidade())
      .precoUnitario(req.precoUnitario())
      .cidade(req.cidade())
      .estado(req.estado())
      .descricao(req.descricao())
      .construir();
  }
}

Cada perfil tem campos completamente diferentes — o Builder permite 3 interfaces específicas sem forçar um super-construtor genérico cheio de null

// validar() no ConcreteBuilder — falha rápido
if (cnpj == null || cnpj.isBlank())
  throw new IllegalStateException("CNPJ obrigatório");
if (estado.length() != 2)
  throw new IllegalStateException("Estado inválido");
Princípios de Design
Como o Builder aplica o SOLID
PrincípioComo o Builder aplica no AgroPlace
S — SRP Responsabilidade única: o Builder cuida exclusivamente da montagem e validação do objeto. O Serviço cuida da regra de negócio. O Diretor cuida da sequência. Cada classe faz uma coisa.
O — OCP Aberto para extensão: para adicionar um campo novo em Anuncio, basta adicionar um método na interface e implementar no ConcreteBuilder — sem modificar o Diretor ou o Serviço.
L — LSP Substituição: AnuncioConcretoBuilder pode ser substituído por qualquer outro ConcreteBuilder sem quebrar o DiretorAnuncio, que depende apenas da interface.
I — ISP Interfaces enxutas: ContaUsuarioBuilder não tem métodos de AnuncioBuilder. Cada interface declara apenas o que é relevante ao seu produto.
D — DIP Inversão de dependência: DiretorAnuncio depende da abstração AnuncioBuilder (interface), não da classe concreta — que é injetada via construtor.

Antes e depois
Antes — Telescoping Constructor
// 12 argumentos posicionais — sem nomes
// Construtor público — qualquer código
// pode criar um Anuncio inválido

new Anuncio(
  conta, titulo, especie,
  raca, quantidade, peso,
  idade, sexo, preco,
  cidade, estado, descricao
);
Sem validação de campos obrigatórios
Trocar 2 parâmetros compila — bug silencioso
Campos opcionais exigem null explícito
Impossível ler sem olhar a assinatura
Depois — Builder + Diretor
// Diretor encapsula o processo de montagem
// construir() valida antes de criar o objeto
// Construtor de Anuncio é package-private

diretor.construirDaRequisicao(conta, req);

// Internamente — fluent chain nomeada:
builder.conta(conta)
       .titulo(req.titulo())
       .cidade(req.cidade())
       .construir();   // ← valida aqui
Validação centralizada em validar()
Campos nomeados — autoexplicativo
Campos opcionais simplesmente omitidos
Objeto inválido nunca sai do Builder
Conclusão
O que o Builder resolve no AgroPlace
Construtor telescópico eliminado
Os 3 módulos criavam objetos com 7–12 parâmetros posicionais. Builder substitui por uma API fluente com campos nomeados.
Validação no momento da construção
O método validar() do ConcreteBuilder garante fail-fast — nenhum objeto inválido chega ao repositorio.save().
Extensível sem modificação
Novos campos podem ser adicionados implementando novos ConcreteBuilders sem alterar o Diretor ou o Serviço — Open/Closed em prática.
