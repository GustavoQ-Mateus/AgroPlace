Sobre o Padrao
O que e o Padrao Builder?

Classificacao GoF: Padrao Criacional (Creational Pattern)
Definido originalmente por Gamma, Helm, Johnson e Vlissides no livro de 1994.

O Builder separa o algoritmo de construcao de um objeto complexo da sua representacao final. Isso permite que o mesmo processo de montagem produza diferentes variantes de um objeto.

Diferente de uma factory que entrega o objeto em uma unica chamada, o Builder monta o objeto passo a passo — cada etapa configura uma parte especifica — e so materializa o produto ao chamar construir().

Factory Method
Delega a criacao a subclasses
Builder
Monta passo a passo
nosso foco
Abstract Factory
Familias de objetos
Os 4 participantes GoF
Builder
Interface que declara os metodos de configuracao para cada parte do produto. Define o contrato de construcao.
ConcreteBuilder
Implementa a interface Builder, acumula o estado interno e executa validacoes em construir().
Director
Orquestra a sequencia de chamadas ao Builder. Conhece o processo, nao o produto resultante.
Product
O objeto complexo sendo construido. Seu construtor e restrito — so pode ser criado via Builder.
Quando Aplicar
Casos de uso do Padrao Builder
01
Objetos com muitos parametros
Quando um objeto exige 5 ou mais parametros no construtor, o Builder substitui a lista confusa por uma API fluente e nomeada.
02
Parametros opcionais
Evita passagem explicita de null para campos opcionais. Apenas os metodos necessarios sao chamados.
03
Validacao centralizada
O metodo construir() e o unico ponto de validacao — garante que nenhum objeto invalido seja criado.
04
Multiplas representacoes
O mesmo Diretor pode usar diferentes ConcreteBuilders para produzir variantes do mesmo tipo de produto.
Exemplos no ecossistema Java

StringBuilder  ·  HttpClient.newBuilder()  ·  Stream.builder()  ·  Locale.Builder

Exemplos no Spring

UriComponentsBuilder  ·  MockMvcRequestBuilders  ·  SecurityFilterChain via lambda

O Problema
Anti-padrao: telescoping constructor

No AgroPlace, a entidade Anuncio exige 12 parametros. Sem Builder, o codigo ficaria assim:

// ANTI-PADRAO — construtor telescopico
new Anuncio(
  conta,
  "Lote Nelore Macho",   // titulo
  "BOVINO",              // especie
  "Nelore",              // raca
  50,                    // quantidade
  new BigDecimal("420.00"), // peso
  24,                    // idadeMeses
  SexoAnimal.MACHO,
  new BigDecimal("3800.00"), // preco
  "Sobral",
  "CE",
  "Animais vacinados, GTA inclusa"
);

Problemas concretos desta abordagem no sistema:

Ilegibilidade
Parametro 5 e quantidade ou peso? Sem IDE, impossivel saber a ordem.
Sem validacao
Nenhum ponto central para checar se preco > 0 ou se estado tem exatamente 2 caracteres antes de persistir.
Acoplamento
Qualquer adicao de campo exige atualizar toda chamada. No AgroPlace ha 3 módulos com objetos de 7 a 14 campos.
Campos opcionais
Campos como raca e descricao forcam null explicito na assinatura do construtor.
Objeto invalido
Um Anuncio com preco negativo ou estado vazio pode chegar ao repositorio.save() sem nenhuma barreira.

Fluxo completo — Criacao de Anuncio
ControladorAnuncio → ServicoAnuncioPadrao → DiretorAnuncio → AnuncioConcretoBuilder → Anuncio 
// ServicoAnuncioPadrao.java
@Override
public RespostaAnuncio criar(
    ContaUsuario conta,
    RequisicaoAnuncio req) {

  DiretorAnuncio diretor =
    new DiretorAnuncio(
      new AnuncioConcretoBuilder()
    );

  Anuncio anuncio =
    diretor.construirDaRequisicao(conta, req);

  return montarResposta(
    repositorio.save(anuncio)
  );
}

O servico de aplicacao nao conhece nenhum campo do Anuncio — delega ao Diretor, que conhece o processo de montagem.

Interface, ConcreteBuilder e Director
AnuncioBuilder.java — Interface
public interface AnuncioBuilder {
  AnuncioBuilder conta(ContaUsuario conta);
  AnuncioBuilder titulo(String titulo);
  AnuncioBuilder especie(String especie);
  AnuncioBuilder raca(String raca);
  AnuncioBuilder quantidade(int qtd);
  AnuncioBuilder pesoMedioKg(BigDecimal v);
  AnuncioBuilder idadeMediaMeses(Integer v);
  AnuncioBuilder sexo(SexoAnimal sexo);
  AnuncioBuilder precoUnitario(BigDecimal v);
  AnuncioBuilder cidade(String cidade);
  AnuncioBuilder estado(String estado);
  AnuncioBuilder descricao(String desc);
  Anuncio construir();
}
AnuncioConcretoBuilder.java — validar()
private void validar() {
  if (conta == null)
    throw new IllegalStateException(
      "Conta e obrigatoria");
  if (titulo == null || titulo.isBlank())
    throw new IllegalStateException(
      "Titulo e obrigatorio");
  if (quantidade < 1)
    throw new IllegalStateException(
      "Quantidade minima: 1");
  if (precoUnitario.compareTo(
      BigDecimal.ZERO) <= 0)
    throw new IllegalStateException(
      "Preco deve ser positivo");
  if (estado.length() != 2)
    throw new IllegalStateException(
      "Estado invalido (use UF)");
}

O construtor de Anuncio e package-private: so o ConcreteBuilder pode instanciar o produto — nenhum codigo externo cria um Anuncio invalido.

Cada tipo de usuario tem campos especificos do seu dominio. O Builder garante que cada perfil seja montado com as regras corretas sem compartilhar logica.

PerfilProdutorConcretoBuilder.java — construir() + validar()
@Override
public PerfilProdutor construir() {
  validar();
  return new PerfilProdutor(this);
}

private void validar() {
  if (conta == null)
    throw new IllegalStateException(
      "Conta e obrigatoria");
  if (nomePropriedade == null
      || nomePropriedade.isBlank())
    throw new IllegalStateException(
      "Nome da propriedade e obrigatorio");
  if (cidade == null
      || cidade.isBlank())
    throw new IllegalStateException(
      "Cidade e obrigatoria");
  if (estado == null
      || estado.length() != 2)
    throw new IllegalStateException(
      "Estado invalido");
}
Vantagens
Por que Builder e ideal para o AgroPlace
✦
Legibilidade do codigo
Cada campo e nomeado explicitamente na chain fluente. Nao ha duvida se o 4o argumento e peso ou quantidade.
✦
Validacao fail-fast
construir() e a unica porta de saida. Nenhum objeto invalido chega ao repositorio — regras de negocio protegidas na camada de dominio.
✦
Campos opcionais sem null
Campos como raca e descricao simplesmente nao sao chamados. Sem sobrecarga de construtores e sem null explicito.
✦
Encapsulamento total do produto
O construtor de Anuncio e package-private. Impossivel criar um produto malformado fora do Builder.
✦
Extensibilidade
Adicionar um campo ao Anuncio requer apenas um novo metodo na interface e no ConcreteBuilder. O Director e o Servico nao mudam — Open/Closed Principle.
✦
Testabilidade
Cada ConcreteBuilder pode ser testado isoladamente. E possivel criar um MockBuilder implementando a interface para testes de Diretor sem dependencias reais.
✦
Separacao de responsabilidades
O Servico cuida das regras de negocio. O Director cuida do processo de montagem. O ConcreteBuilder cuida dos campos e validacoes. Clean Architecture respeitada.
✦
Consistencia entre modulos
Os 3 modulos (autenticacao, anuncio, perfil) seguem exatamente o mesmo padrao. Qualquer desenvolvedor que entra no projeto entende imediatamente a estrutura.
Principios SOLID
Builder e SOLID — como se complementam
Principio Como o Builder aplica no AgroPlace Evidencia no codigo
S — SRP Builder cuida exclusivamente da montagem e validacao. Servico cuida da regra de negocio. Director cuida do processo. Cada classe tem uma unica razao para mudar. ServicoAnuncioPadrao nao conhece campos de Anuncio
O — OCP Para adicionar fotoPrincipal ao Anuncio, basta um novo metodo na interface e no ConcreteBuilder — sem alterar Diretor ou Servico. Interface AnuncioBuilder define contrato extensivel
L — LSP Qualquer novo ConcreteBuilder que implemente AnuncioBuilder pode substituir AnuncioConcretoBuilder no Diretor sem quebrar comportamento. DiretorAnuncio depende apenas da interface
I — ISP Cada Builder tem apenas os metodos do seu produto. ContaUsuarioBuilder nao tem metodos de AnuncioBuilder — interfaces enxutas e coesas. 5 interfaces distintas para 5 entidades
D — DIP DiretorAnuncio recebe um AnuncioBuilder (interface) no construtor, nao um ConcreteBuilder. Depende da abstracao, nao da implementacao. new DiretorAnuncio(new AnuncioConcretoBuilder())
Comparativo
Antes e depois — impacto real no codigo
Antes — Telescoping Constructor
// 12 parametros posicionais
// sem validacao, sem nomes
new Anuncio(
  conta, titulo, especie,
  raca, quantidade, peso,
  idade, sexo, preco,
  cidade, estado, descricao
);
Objeto invalido pode ser criado
Ordem dos parametros causa bugs silenciosos
Campos opcionais forcam null explicito
Leitura impossivel sem IDE
Qualquer novo campo quebra todas as chamadas
Depois — Builder + Director
// Fluent API nomeada
// validar() chamado em construir()
diretor.construirDaRequisicao(
  conta, req
);

// internamente:
builder.conta(conta)
  .titulo(req.titulo())
  .especie(req.especie())
  .precoUnitario(req.precoUnitario())
  .construir(); // valida aqui
Validacao centralizada em validar()
Campos nomeados — legibilidade total
Campos opcionais simplesmente omitidos
Produto invalido nunca sai do Builder
Novos campos nao quebram o Servico
Conclusao
Builder no AgroPlace — resumo
Problema resolvido
Os 3 modulos criavam objetos com 7 a 12 parametros posicionais. O Builder substituiu por uma API fluente nomeada, segura e extensivel.
Validacao garantida
validar() no ConcreteBuilder garante que nenhum objeto invalido chega ao repositorio.save() — fail-fast antes da persistencia.
Arquitetura limpa
Padrao aplicado em sincronia com Clean Architecture — Builder vive no dominio, Diretor na aplicacao, sem vazamento de dependencias.
